# 私辞典｜端末間同期の設計（2026-11-09）

## 0. 結論
Quick LinksのCloudflare Worker / R2を共有基盤として再利用し、私辞典専用のランダムなvault IDと秘密鍵を使う。現行のIndexedDBを主な保存先のまま残し、同期を任意で有効化する。利用者が普段行う操作は「言葉を拾う」「必要なら編集する」だけ。同期作業を日課にしない。

## 1. 守：前提から考える
- 解決したい問題：PC・スマホで保存した言葉が分断され、再登録・手動バックアップが必要。
- 解決しなくてよい問題：多人数で編集する共同辞書、リアルタイム共同編集、ユーザーアカウント。
- 維持すべき強み：オフラインで使える／高速な検索／使い始めにログイン不要／JSONで持ち出せる。
- 同期は保存先の置き換えではなく、端末内データの複製・差分の統合。
- 同期済み表示は「最後にサーバーへ反映できた」と伝える。あらゆる端末への即時配信完了と混同させない。

## 2. 破：Quick Linksから学び、私辞典用に変える
確認した既存実装：silovar-uk/quicklinks の sync.js と worker/src/index.js。
- Workerのエンドポイント：/v1/vault/{vaultId}（GET/PUT/OPTIONS）
- アクセス制御：Authorization Bearer / 保管ID / 保管ごとの認証ハッシュ。
- 暗号化封筒：quick-links-cipher-v1 / iv / ciphertext。Workerは暗号文のみ保管。
- 排他制御：ETag、If-Match、If-None-Match。競合時は再取得・再統合。
- Origin：silovar-uk.github.io、localhost。MyDictionaryは同じOrigin。
- 上限：暗号文封筒を含めたリクエスト本文5MiB。
- Quick Linksはローカルの変更と共有状態を基準点から三者統合。私辞典では辞書項目をフィールド単位でマージし、最初の別端末ではID別に統合する。

私辞典固有の注意点：
- `DictionaryEntry` に独立したIDと更新日時・削除日時がある。
- タグはnormalizedNameがユニークなので、端末ごとに生まれた同名タグのIDを連携時に一本化する。
- 閲覧回数・ランダム表示回数は通常の説明文と異なる。単純加算では二重計上するため、現行案は両端末の最大値を採用する（全端末合計を厳密には数えない）。
- ソフト削除はdeletedAt、完全削除は同期基準点からの欠損をtombstoneとして送る。
- バックアップのsettingsには秘密鍵も同期基準点も含めない。
- ページを閉じた直後は通信が中断されうる。次回起動時に再試行し、同期済みと誤表示しない。

## 3. 離：UXの原則
1. **言葉が主役**：ヘッダーに小さな同期状態、詳しい設定は「データ」に集約。
2. **最初だけ意識**：初回に「同期をはじめる」、別端末ではリンクを開いて確認。以後は自動。
3. **不意に消えない**：初回結合は上書きでなく統合。競合は選択式。削除と編集の衝突も確認。
4. **機内モードでも使える**：保存・検索・閲覧は常にローカルから。通信復帰後に同期。
5. **安心を可視化**：「同期済み」「同期待ち」「同期エラー」「要確認」と最終同期時刻。
6. **主導権を残す**：手動同期、連携解除、JSONバックアップ。

## 4. データフロー
1. Dexie IndexedDBに編集を確定し、画面に反映。
2. 変更イベントで同期予定を登録（約1.2秒後）。開き直し／オンライン復帰／90秒の定期確認でも同期。
3. ブラウザーでローカルと最終同期基準点を読み込み、Workerから暗号化スナップショットを取得。
4. 復号・形式検証後、基準点を使って3-way merge。
5. 同じフィールドが双方で異なれば、勝手に勝者を決めず同期を保留し選択を要求。
6. 共有データが変わる場合は条件付きPUT。412等なら最新状態を取り直す。
7. 同期中に追加編集があれば端末データを上書きせず、同期予定として維持。
8. 変更が必要な場合のみDexieのトランザクションで適用し、基準点を更新。

## 5. 技術と守るべき不変条件
- 暗号化：Web Crypto API、HKDFで暗号化鍵と認証鍵を別々に導出、AES-GCM（ランダム96-bit IV）。
- 辞典専用のHKDF salt/infoとvault IDを使い、Quick Linksの辞典と保管領域・鍵を分離。
- 端末への秘密鍵保存はローカルストレージ。自分の端末のみで連携リンクを開く。
- 完全復元は連携解除後。復元が同期基準点を変えてデータ消失を起こす事故を防止。
- Workerが返す条件付き書き込みエラーは、黙って上書きせず再取得して再統合。
- 同期はバックアップではない。誤削除・鍵の紛失・サーバー停止に備えJSONバックアップを推奨。
- 同じGitHub Pages Originで動く別のアプリもブラウザー保存領域にアクセスできる点は注意。将来的に機密性を高めるなら専用サブドメインと別の保存Originを検討する。

## 6. 検証項目（受け入れ条件）
- [ ] 既存20件がある端末で開始→別の空端末で20件受け取れる
- [ ] PCとスマホで別々の言葉を追加→両方に残る
- [ ] 同じ言葉の別フィールドをオフラインで編集→統合
- [ ] 同じフィールドを違う値に変更→選択を求める
- [ ] 別端末で完全削除と編集を競合→安全に確認
- [ ] 同名タグのIDが別々でも一つにまとまる
- [ ] iPhone Safariの中断・再起動でも同期できる
- [ ] 端末をオフラインにして保存→再接続で復旧
- [ ] 5MiB超のデータ→端末データは失わず明示的にエラー
- [ ] 共有リンク受信後にURLから鍵が消える
- [ ] 連携解除しても端末の言葉はそのまま
- [ ] 未設定端末の挙動・既存バックアップの互換性が変わらない

## 7. 段階的な拡張
- MVP：既存Worker再利用、暗号化、端末連携、自動同期、保守的な競合解決、状態表示、バックアップ。
- 次：端末の名前と最終アクセスを表示、同期履歴、削除からの復旧、QRコードでのペアリング。
- 将来：辞書が5MiBを超える場合の差分API・チャンク化、オプションとして履歴の累積カウンター／自動鍵更新、専用オリジン。
