# 私辞典｜次のUX開発を進めるための実行プロンプト（2026-11-10）

あなたは、私辞典のUXリード、ユーザーリサーチャー、フロントエンドエンジニア、データ整合性監査担当を兼ねる開発チームです。指示をそのまま実装するのではなく、**本当に解くべき問題を先に再定義**してください。

## 1. 対象と一次資料
- 公開URL：https://silovar-uk.github.io/mydictionary/
- リポジトリ：https://github.com/silovar-uk/mydictionary
- 製品仕様：docs/NEXT_UX_SPEC_20261110.md
- 前段のUX設計：docs/UX_REDESIGN_20261110.md
- 同期設計：docs/SYNC_DESIGN.md
- 現行の実装（最終的にはmain最新版を直接確認）：src/domain/types.ts、src/domain/normalize.ts、src/db/database.ts、src/services/entries.ts、src/services/sync.ts、src/services/transfer.ts、src/components/QuickAdd.tsx、src/pages/AddPage.tsx、src/pages/DictionaryPage.tsx、src/components/EntrySheet.tsx、src/domain/discovery.ts。

**重要**：以前の会話や仕様書の記述を最新のコードより優先しない。実際に読めるコードや動作と食い違う場合は差異を記録し、仕様の修正を提案する。推測を既成事実にしない。

## 2. 実行目的
ユーザーが過去に拾った言葉を再度入力したとき、過去の文脈を自然に思い出せるようにする。ただし、**言葉を保存する速さ・安心・自由を絶対に損なわない**ことを主目的とする。

最初の開発単位は「再会リボン」のRead-only MVP。既存の同表記エントリーを表示するだけで、統合・書き換え・スキーマ移行を行わない。

### 成功定義
1. はじめての言葉は従来どおり速く保存できる。
2. 過去に同表記を拾った場合、そのときの意味や出典を発見できる。
3. 同表記でも意味の違う言葉を安全に別登録できる。
4. 既存データ・端末間同期・下書き・JSONバックアップに回帰がない。
5. PCとスマホの入力導線で自然に表示され、強制ダイアログはない。

## 3. 思考の3担当を必ず独立して走らせる
### A. 前提を疑う担当（守）
- 「重複は残すべき」「再会は価値がある」「登録時に提示すれば嬉しい」という前提をそれぞれ反証する。
- 重複提示で入力が遅くなる・ストレスになる可能性を、実際の登録フローに照らして評価する。
- 既存コード、業務・UX原則、具体的なユーザーシナリオを分け、事実と仮説を区別する。
- 何を作らないか、何を守るかを明示する。

### B. リサーチ担当（守→破）
- 現行コードの読み取り、ソース付きUXリサーチ、関連先行プロダクトの事例を収集。
- 少なくとも「認識と想起」「段階的開示」「編集時のデータ喪失防止」「フォーカス／IME」「ローカルファースト」の観点を扱う。
- 最初のリサーチから未解決の問いを3件以上導出し、それを狙って**再リサーチ**する。
- 情報源URL・確認日・何を裏付けるか・採用しない論点まで整理する。
- 意外な異分野（博物館の展示札、観察日誌、Gitの履歴、カード目録など）を横断。ただし例え話で終わらず、UXの具体策に翻訳する。

### C. 実装手順担当（破→離）
- 技術的な依存関係、失敗時の戻し方、検証用fixture、実装順序を定義。
- Phase 0を小さな独立PRに切り出す。Phase 1（二画面）・Phase 2（再会履歴DB拡張）は混ぜない。
- UIに先立ち、保存・下書き・同期の回帰テストを書けるようにする。
- 不明点が残っても、重大な破壊的仕様でない限り安全な仮定を明記して進める。重大なデータ損失リスクがある場合は機能実装を止め、代替の読み取り専用案に切り替える。

## 4. 作業工程：リサーチ→構造化→再リサーチ→実装→検証
1. **現行の体験を観察**：PC/スマホで、新規語登録・重複登録・詳細閲覧・入力中断を操作単位に分解。実機が使えない場合はその制限を明記する。
2. **課題を構造化**：「発見できない」「登録が遅い」「入力を失う」「統合で意味が壊れる」「同期で損失する」等を独立の論点にする。
3. **調査と再調査**：不足する証拠を重点的に探す。外部の研究結論とこのアプリの仮説を混ぜない。
4. **仕様との差分整理**：docs/NEXT_UX_SPEC_20261110.md の要求ID AC-01～AC-15を現行実装へ対応付け、必要ならADRで仕様変更を記録。
5. **テスト先行**：ゼロ件・1件・10件の同名語、NFKC/大小文字/仮名の正規化、別義、削除済み、IME、日本語全文、オフライン、同期済み二端末のケース。
6. **実装**：`src/domain/reunion.ts`（純粋な一致判定）、`src/components/ReunionRibbon.tsx`（read-only UI）を中心に、QuickAddとAddPageへ接続。既存createEntryを変更しない。
7. **UXレビュー**：320/390/768/1100/1440/1920px、入力フォーカス、下書き、Tab/Enter/Esc、スクリーンリーダー、入力停止・再開を評価。候補が10件以上でも保存ボタンを邪魔しない。
8. **CI**：typecheck、テスト、buildの成功を確認し、操作の受入チェックリストに結果を記入。ローカルの自動テストだけで「実機確認済み」と表現しない。
9. **PR**：変更点・スクリーンショット（取得できる場合）・テスト結果・未検証事項・ロールバック方法を記載。機能を実際に変更したか、仕様書だけか、公開まで完了したかを明確に分ける。
10. **次の判断**：再会リボンの利用価値が示された場合のみ、Phase 1（PC一覧＋詳細）とPhase 2（時系列の再会履歴）を検討する。

## 5. 禁止事項
- 一致する文字列を本人の確認なしに統合、削除、上書きしない。
- 「同じ表記＝同じ意味」「同じ表記を二度拾う＝思想が変わった」と断定しない。
- UI表示だけのために、同期ペイロードやDBを移行しない。
- 履歴機能を作る場合は、Dexieのマイグレーション、旧アプリとの同期互換、旧バックアップ復元、削除・競合を設計せず実装しない。
- 端末のlocalStorage・IndexedDBを消去して不具合を解決しようとしない。
- 単語・出典・個人メモの生データを外部計測基盤に送らない。
- 見た目の演出だけで「驚きを実現した」と評価しない。

## 6. 最終出力の形式
次の順で報告する。短い見出しでも全体の論理が追えるようにする。

1. **結論・今回の一手**：実装範囲、やらないこと、採否理由。
2. **事実と仮説**：コードから確認した事実／外部文献／仮説／反証。
3. **研究と再リサーチ結果**：原理・盲点・異分野の洞察、出典URL。
4. **UXの状態遷移**：画面ごとの具体的な行動、例外、コピー。
5. **技術設計**：ファイル単位の変更、純粋関数、データ構造、同期保全。
6. **テスト結果**：AC-01～AC-15の合否と未検証の区別。
7. **PR・公開状況**：実際のリンク、実装済み／未実装、CI・デプロイ状態。
8. **次の意思決定**：観察データを得る具体的方法、Phase 1/2のGo/No-Go、最初に着手する操作。

ユーザーがまだ言語化していない困りごとを探し、提案で終わらず**検証できる最小成果物**に落とすこと。便利さを驚きより優先し、驚きは使い続けた人への副産物として設計する。
